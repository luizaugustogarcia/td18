# RTX 5090 / EPYC launch profiles

For instance 60769368 (211.21.106.84), use the attached `/workspace` volume.
These are initial profiles for the advertised 256 CPUs and approximately
256 GB RAM, not measured optima on that host. Both launchers detect the actual
CPU affinity, cgroup CPU quota and memory limit inside the container. They use
JDK 21 and JShell, and share one workspace lock so emitter and checker do not
compete for the same memory and CPU budget.

The 5090 has compute capability 12.0. Build native code for `sm_120` using
CUDA Toolkit 12.8 or 13.0, within the advertised driver capability. A CUDA
version shown by `nvidia-smi` is not an installed toolkit. The emitter build
checks that `nvcc` supports `sm_120` and compiles only native 120 plus forward
PTX. See [NVIDIA specifications](https://www.nvidia.com/en-us/geforce/graphics-cards/50-series/rtx-5090/)
and [CUDA 12.8 release notes](https://docs.nvidia.com/cuda/archive/12.8.0/cuda-toolkit-release-notes/index.html).

## Build and start

Run from the repository checkout on the new server with JDK 21, Maven,
Python 3, `flock`, and (for the emitter) CMake 3.24+ and the CUDA toolkit on PATH.
Configure `JAVA_HOME`, CUDA PATH and library paths in `~/.bashrc`. The checkout
may live under `/workspace`; database, scratch, native build, temporary JNI
files, logs and run settings use `/workspace/td18` by default.

```bash
bash -ic './tools/run-5090-emitter.sh --build'
bash -ic './tools/run-5090-emitter.sh --dry-run'
nohup bash -ic './tools/run-5090-emitter.sh' > /workspace/td18/logs/emitter-launcher.log 2>&1 < /dev/null &
tail -F /workspace/td18/logs/emitter-latest.log
```

After emission completes, or after copying a closed certificate database to
`/workspace/td18/certificates`, launch the checker:

```bash
bash -ic './tools/run-5090-checker.sh --build'
bash -ic './tools/run-5090-checker.sh --dry-run'
nohup bash -ic './tools/run-5090-checker.sh' > /workspace/td18/logs/checker-launcher.log 2>&1 < /dev/null &
tail -F /workspace/td18/logs/checker-latest.log
```

Both commands run the complete scope. Each invocation creates a new work path;
the checker always regenerates its own obligations. To resume compatible
emitter work instead of regenerating its initial phases:

```bash
bash -ic './tools/run-5090-emitter.sh --resume-work=/workspace/td18/work/previous-emitter-run'
```

No launcher removes old data. The volume must hold the certificate database,
the active work sets and temporary compaction output. The default startup
guard requires 32 GiB free; it is not a whole-run capacity guarantee. Avoid
copying unused historical scratch sets onto the 256 GB volume.

## Tuning overrides

Use `--dry-run` to inspect settings without building, allocating GPU memory or
creating files. Environment overrides are `TD18_RUN_ROOT`, `TD18_CERTIFICATE_DB`,
`TD18_CPU_WORKERS`, `TD18_HEAP_GIB`, `TD18_WRITERS`, `TD18_BUFFER_KEYS`,
`TD18_QUEUE_BATCHES`, `TD18_GENERATED_BATCH_KEYS`, `TD18_SCAN_BATCH_KEYS`,
`TD18_LOOKUP_BATCH_KEYS`, `TD18_LOOKUP_PIPELINES`, `TD18_GPU_SLOTS`,
`TD18_GPU_BUDGET_MB`, `TD18_GPU_QUEUE_CAPACITY`, and `TD18_MIN_FREE_GIB`.
`TD18_CERTIFICATE_WRITERS` controls the emitter certificate persistence pool
(32 by default). One coordinator partitions each bounded batch by full key,
and waits for every shard before advancing to the next batch or flushing.
Each shard bulk-checks certificate keys for obstruction markers, then independently
sorts, builds and ingests exact SST files for keys without markers, bypassing
per-key memtable insertion. Only keys with existing markers and obstruction-only
requests retain atomic WriteBatch updates; a few markers cannot force the other
keys back through memtables. Stable sorting preserves the last queued certificate
for duplicate keys; disjoint shard keys and inter-batch barriers preserve
witness/obstruction precedence. Every write still disables WAL; asynchronous failures abort
the run and completed persistence boundaries flush explicitly.
For example, compare 16 slots at 1792 MiB against the default 32 at 896 MiB;
both use 28 GiB of queues. Compare identical immutable samples with
`tools/audit/BenchmarkGpuSearch.jsh`, replaying every successful result before
choosing the faster profile. Do not infer throughput from advertised TFLOPS.
CPU worker and batch tuning should measure useful throughput, core utilization,
GC time and persistence queue pressure, not CPU percentage alone.

The emitter performs a free-VRAM check before Java launch. Native initialization
also checks exact per-slot allocations, including caches and metadata, against
current free VRAM. Run settings record revision, exact JVM options, work path,
exit status and completion times. Successful process exit also requires the
module's completion message. A completed emission still requires a successful
full independent checker and the other research-plan artifacts before any
TD(18) proof claim.
